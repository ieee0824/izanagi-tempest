# #36 手動ログイン入口の設計

対象はアカウント所有者による固定 Claude Code 2.1.325 の公式ログイン1回です。
実行時は #36 の台帳にある実体とライブラリの digest を照合します。
申請 #17530 は実施場所についての質問を受けた段階です。

## 実装差分

| 現行箇所 | 実ログイン入口の変更 |
| --- | --- |
| `claude_offline.rs` の `isolated_command` と `run_pty_child` | 固定の別入口で、検証済み `/bin/claude` と固定 argv `auth login` だけを起動する。入力は管理者同席の既存 PTY、出力は owner が直接見る端末に渡す。端末の録画・ログ転送を無効にし、元の環境を消去した上で専用 HOME・CLAUDE_CONFIG_DIR と固定通信設定を渡す。 |
| `verify_waiting_network_for` と `local_auth.rs` | 実行世代の netns FD、固定ルール、認証専用ゲートウェイの識別を照合してから許可する。固定子は起動直前に同じ netns を確認する。合成用のポートや負例引数は新入口に含めない。 |
| `writable_config.rs` | 新規0700の設定世代だけを書き込み可能にする。実運用では合成用の空ファイル判定を、事前合意した名前・種別・所有者・権限・リンク数の監査に置き換える。未知のエントリは保持成功と判定しない。 |
| 監督の終了処理 | 手動完了、失敗、期限、PTY 切断を区別し、通信経路の閉鎖、PID 名前空間の停止、mount 解除、設定世代の処理を照合する。 |

## CLI とブラウザーの通信境界

owner は自身のブラウザーで公式のサインインを操作します。ブラウザー側の
候補は `claude.com` と `claude.ai` です。組織の SSO や追加の宛先が必要な
場合は、実施前に利用条件を確定します。

CLI 側の OAuth 交換先候補は `platform.claude.com:443` です。CLI の名前空間は
既定拒否とし、実行世代専用の CONNECT ゲートウェイへの通信だけを許可します。
CLI からの直接 DNS、外部 IP への直接接続、IPv6 等の別経路は閉じます。
ゲートウェイは固定名とポートの組だけ受理し、自身の管理されたリゾルバーで
その名だけを解決します。ループバック、プライベート、リンクローカル等の
応答は拒否し、検証済みアドレスに接続先を固定します。各接続に期限を設け、
応答がない場合や許可条件が変わった場合は中断します。
モデル API、MCP、テレメトリの宛先には経路を開きません。

ゲートウェイは TLS をそのまま中継し、サーバー証明書は CLI が検証します。
宛先照合だけでは、許可ホスト内の HTTPS パスや操作を区別できません。
同一ホスト内で認証操作に限定する実行条件は、固定 CLI の公式ログイン入口と
owner の操作範囲に依存します。ネットワークで操作単位まで強制することが
必須なら、ベンダーが分離した認証専用宛先を確認できるまで起動を保留します。
固定版の CONNECT 対応、最小宛先、ブラウザーから CLI への引き継ぎ方式は
未実測です。未承認先や追加の転送が必要な場合は、その場で許可範囲を広げず
終了します。
[Claude Code のネットワーク要件](https://code.claude.com/docs/en/network-config#network-access-requirements)

## 実施者・保存・終了

- ホスト管理者は既存端末の操作者と PTY の有無を確認し、固定実体、
  起動前の境界、世代領域、通信停止手順を準備します。既存端末で同席して
  その固定入口を起動します。
- owner は usage credits 無効を確認し、外部接続範囲、端末への引き継ぎ、
  保持期限と廃棄担当に合意した上で、手動ログイン単独の承認を行います。
  認証 URL・コードは owner の手元だけで扱います。
- Linux での保存候補は専用 `CLAUDE_CONFIG_DIR/.credentials.json` の0600です。
  付随ファイルと一時領域の許容範囲は実行前に確定します。観測は固定項目の
  結果とファイルのメタデータに限定し、内容やハッシュは採取しません。
  保持する場合も同一世代・期限付きとし、廃棄責任者を記録します。
  [Claude Code の認証と保存先](https://code.claude.com/docs/en/authentication#credential-management)
- 終了・中断・切断時はゲートウェイを閉鎖し、PID 終了と mount 解除を確認します。
  異常時に終了や保存範囲が不明なら、世代をアクセス制限下に残して再利用を
  拒否し、管理者と owner に引き継ぎます。認証が成立した可能性がある場合の
  取消は owner が判断します。

初回のモデル実行、本番 B/VM、MCP は別判断です。この設計の作成では、
ログインモードの起動、外部接続、SSH 設定や権限変更は行いません。

## 固定入口の起動前確認

`tempest-claude-manual-login` は引数を受け付けず、管理者と標準入出力・
標準エラーが共有する PTY を確認します。管理者設定の候補位置は
`/etc/tempest/claude-manual-login.json` です。管理者所有・0600・単一リンクの
通常ファイルを固定パスから開き、4 KiB 以下の JSON を検証します。
現段階で有効な項目は `{"version":1,"authority":"platform.claude.com:443"}`
です。この設定は認証先候補を確認するもので、起動許可を表しません。
管理 DNS、許可する
アドレス、認証ファイルの保存条件と保持期限、および TLS 透過の制約への
合意を得てから、設定を受理する処理を実装します。owner の承認は実施ごとに
確認します。現段階の入口はいずれのケースでも子プロセスやゲートウェイを
起動せず、設定世代の作成も行いません。

```sh
cargo build -p tempest-linux-probe --locked --bin tempest-claude-manual-login --bin tempest-claude-offline-local-auth-pty
sudo python3 integration/claude_local_auth_pty_smoke.py target/debug/tempest-claude-offline-local-auth-pty
```

cc-sakura #17589 への承認 #17590 は、認証ホストとポートを制限する設計の
実装を進める判断です。TLS の検証は固定 CLI が行い、透過ゲートウェイでは
許可ホスト内の HTTPS 操作を区別できません。実ログイン、外向き認証通信、
認証情報の保持には、それぞれ該当する実施判断が必要です。

ゲートウェイは CONNECT の宛先を確認してから、事前に照合した IP とポートへ
接続します。接続済みのソケットの相手がこの組と一致した場合にだけ成功を返し、
以後はバイト列をそのまま中継します。現行試験では上流の応答をループバックに
置き、宛先不一致時に成功応答や中継を行わないことを確認します。

## #144 の VM 合成試験

Ubuntu 24.04 の使い捨て VM で、QEMU ユーザーネットワークの
`restrict=on` を維持して再現しました。ゲストの libc6 は
`2.39-0ubuntu8.9`、固定ハッシュの採取元は `2.39-0ubuntu8.12` です。
初回は、ゲストの固定ローダーと glibc 5点がすべてハッシュ不一致だったため、
事前照合で停止しました。

1. ホストで上記の合成バイナリをビルドする。試験スクリプトと import 先、
   固定 BusyBox、nftables と不足する依存パッケージ、固定ローダーと glibc
   5点の SHA-256 一覧を作る。固定 CLI の期待値は
   [固定成果物の記録](ISSUE-36-GATES.md)と同じものを用いる。
2. VM に試験用ファイルだけを SSH で転送し、SHA-256 を照合する。
   nftables はパッケージを一時ディレクトリに展開し、一時入口から起動する。
3. root の `unshare --mount --propagation private` 内で `/var/lib` を
   一時 overlay にし、固定 CLI を `/var/lib/tempest-claude-offline/claude`
   に root 所有、単一リンク、0555 で配置する。ローダーは0555、他の
   ライブラリは0444の root 所有・単一リンクとし、各固定
   `/usr/lib/x86_64-linux-gnu` パスに読み取り専用で bind する。
   固定パスから期待 SHA-256 を再照合し、不一致なら試験を開始しない。
4. `/var/lib/tempest-claude-version-work` と
   `/var/lib/tempest-claude-config-fixture` を root 所有・0700で作り、
   名前空間内で上記の `claude_local_auth_pty_smoke.py` を実行する。
   作業親が両方とも空になったことを確認し、名前空間を終了する。
5. 名前空間外から、固定ライブラリの bind と作業親が残っていないこと、
   ゲストの libc6 が元の版のままであることを確認する。一時入口、
   試験用ファイル、搬入用公開鍵を回収し、その鍵での再接続が拒否される
   ことを確認する。

実測ではスモークが終了コード0を返しました。許可した合成上流への接続に
成功し、別ホストと直接3ポートは拒否されました。許可なし・期限切れ・
再提示も拒否され、切断後に子プロセス、トンネル、リスナー、設定世代を
回収しました。両作業親は空で、VM の通常の libc6 と通信制限を維持し、
搬入用の一時鍵で再接続できないことを確認しました。
[Issue #144 の試験記録](https://github.com/ieee0824/izanagi-tempest/issues/144)

## 実入口での起動前拒否

Linux ホスト上で、実入口 `tempest-claude-manual-login` を
`unshare --mount --net --propagation private` で隔離しました。ネットワーク
名前空間には停止したループバックだけがあり、IPv4 と IPv6 の経路は
ありませんでした。隔離した `/etc` に root 所有・0600・単一リンクの
有効な設定を置き、root で標準入出力・標準エラーを同一 PTY に接続しました。

実入口は `manual login refused: administrator policy acceptance disabled`
と出力して終了コード1を返しました。システムコール追跡では子プロセスの
生成、ソケットの作成、マウントやディレクトリ作成はなく、作業親の内容も
前後で同じでした。VM の合成試験では制限付き接続と終了時の回収を確認し、
実入口の隔離試験では現行の起動前拒否を確認しました。実認証先への通信、
ログイン、ログイン後の認証情報の保持と回収は未検証です。

v2 の設定診断では、許可の対象ホスト名を起動プロセスから見える
Linux ホスト名と照合し、認証先と許可 IP 一覧の版も照合します。
残存時間の上限60秒は診断専用です。運用時の開始期限上限は
別途決定します。有効な v2 設定でも実入口は起動を拒否します。

## 管理対象と承認の照合

実運用では、管理者が確認した対象の登録 ID と、その対象に配布した
設定の対応を管理側で保持します。起動プロセスから見えるホスト名は
補助的な照合に使います。登録 ID は、承認の申告値とは独立した
管理側の情報から取得し、対象 VM の識別と設定配布の記録に結び付けます。

起動側は、開いた固定 CLI から得た SHA-256、固定引数、管理側が確認した
登録 ID、正規化済みの認証先、許可 IP 一覧の版を一つのスコープとして扱います。
許可 IP 一覧の版は同じ内容に対して固定し、変更には新しい版を割り当てます。
承認の署名対象には、スコープ全項目、単回 ID、開始期限、承認の用途と
対象環境を含めます。管理側が登録した承認者鍵と承認権限を確認し、
用途に固有の形式で署名を検証してから、全項目をローカルのスコープと
照合します。起動準備と通信制限にはこの照合済みの値を引き継ぎます。
照合に成功した場合だけ消費記録を同期し、その後に起動を許可します。

合成 PTY の一回許可では、ダミー設定を固定スコープと照合し、CLI、
引数、対象 ID、一覧の版のいずれかが異なると、作業世代や消費記録を
作らずに拒否することを確認します。合成入力の対象 ID は試験の固定値です。
管理側の対象登録や署名検証は今後の結線で行います。

実入口のオフライン診断では、有効な v2 設定と同じ管理ディレクトリに
`claude-login-diagnostic-handoff`、`claude-login-diagnostic-signature`、
`claude-login-diagnostic-trust-key`、`claude-login-diagnostic-target-registration`
を用意します。各ファイルは root 所有・
0600・単一リンクとし、信頼鍵には独立して配置したテスト公開鍵の
生32バイト、署名には Ed25519 署名の生64バイトを使います。
管理側が独立に配置する診断用登録 JSON の `target_hostname` を検証済み設定の
ホスト名と照合し、登録の `target_id` を署名済み入力と照合します。ID は
1〜128 バイトの ASCII 英数字、ハイフン、アンダースコアを使用できます。
診断時刻が設定と署名済み入力のうち早い方の期限に達した場合は拒否します。
正しい署名を照合できても実入口は終了コード1で起動を拒否します。

### 停止要求と監督中の実行の照合

管理側は確認済みの実行 ID と作業世代を組にして停止要求に指定します。
監督側は起動時に固定した作業世代の識別子と、現在有効な実行 ID の両方を
照合し、一致した場合だけ、その実行専用の停止チャネルへ通知します。
停止が受理された実行や終了済みの実行は、後続の要求を別実行へ転送しません。
合成試験では作業ディレクトリの固定 FD のデバイス番号と inode を世代の
識別に使います。運用では再起動や inode 再利用でも過去の実行と衝突しない
実行 ID を管理側で発行し、停止の受付から終了確認まで同じ監督に紐付けます。
回収は PID 名前空間の終了とマウント解除の確認後に進めます。

合成 local-auth PTY のスモーク試験では OpenSSL で一時 Ed25519 鍵を
生成し、管理側設定と署名付き入力を準備します。署名から得た許可 ID を
既存台帳で消費し、設定と署名の早い方の期限を起動許可直前に再確認します。
試験はループバックだけを有効にした、外向き経路のない名前空間で実施します。

合成 local-auth PTY の `signed-administrator-stop` では、消費済み許可 ID と
固定された作業世代のデバイス番号・inode を試験の管理側へ通知します。
試験の管理側は専用設定親ディレクトリに root 所有・0600 の停止 JSON を
原子的に配置します。監督は稼働中の照合に成功した場合だけ管理者停止として
扱い、対象の PID 名前空間を回収します。スモーク試験では PTY を開いた
まま停止し、子孫の終了を pidfd で確認します。旧世代の要求を置いた状態でも
次の実行が起動することを照合します。

実入口の署名診断では、固定 CLI の読み取り照合後に、設定と同じ管理
ディレクトリの `claude-login-diagnostic-ledger` を開きます。台帳は
root:root 所有・0700 の実ディレクトリとし、固定 FD から許可 ID の
記録が存在しないことを確認します。リンクを含む既存エントリがあれば
拒否します。この読み取りは一回消費の予約を作らず、診断成功後も実入口は
終了コード1で起動を拒否します。

### 管理ファイルの一括公開（合成検証）

全入力とダイジェスト一覧を新規世代に書き、ファイル・世代ディレクトリ・
親を同期します。管理側は単一のロック内で、未確定マーカーを先に同期し、
新しい現在版レコードを原子的に置換してから親を同期します。旧版の
再提示は現在版との不一致で拒否し、公開要求も現在版より大きい版だけを
受け付けます。許可の最終消費は同じロック内で現在版を照合し、
現在版が公開領域と独立した管理側の最低版以上であることを確認します。
旧版一式と現在版レコードがともに戻った場合もここで拒否します。
消費は世代とは独立した台帳に排他的に記録します。先に確定した消費は切替後も残り、
切替が先に確定した場合は旧版の消費を拒否します。

現在版を置換した後に親の同期が失敗した場合、未確定マーカーを保持し、
許可の消費を停止します。再起動後は現在版が保留版と一致し、管理側から
独立に得た最低版以上で、世代全体を検証・同期できた場合だけ保留を解除
します。不一致の場合は管理側で復旧するまで停止します。

```sh
python3 -m unittest discover -s tests -p test_claude_generation_publication.py -v
```

試験は同じファイルシステム上で同期エラーを注入し、状態を開き直して
確認します。電源断や実運用ストレージでのクラッシュ耐性は未検証です。

最低版は管理者が公開領域から独立した管理ディレクトリで更新します。
新世代の検証後に共通ロックを取得し、未確定マーカーを永続化してから、
最低版を単調に引き上げます。一時ファイルの同期、原子的な置換、管理
ディレクトリの同期を完了した後に現在版を切り替えます。消費側は同じ
ロックの内側で固定ディレクトリ FD から最低版と現在版を読み直し、
保留がなく、版が一致する場合だけ台帳の最終消費へ進みます。最低版だけ
進んだ状態では旧版・新版とも拒否し、管理者は最低版を下げずに同じ版の
切替を再開します。

Rust の固定 FD 試験では、最低版の永続化直後・現在版の切替前に中断を
注入し、別 FD のロック競合、両版の消費拒否、最低版ファイルのリンク拒否を確認します。
続けて現在版を同じ新版へ置換し、親同期の失敗を注入します。保留中は
台帳が変わらず、管理側が同じ FD のディレクトリを照合・同期してから
保留を解除した場合だけ、新版を消費できることを確認します。

正規運用の順序は、保留の永続化、最低版の永続化、現在版の切替です。
合成試験では原因を切り分けるため、Rust で最低版のみ進んだ状態を
先に構成し、次に保留が残ったまま現在版の親同期に失敗する状態を
検証します。Python では保留の永続化から現在版切替までを検証し、
独立した最低版は消費・復旧時の入力として与えます。Python の追加合成試験では、
保留の同期から独立した最低版の同期、現在版の置換と親同期までを通し、
共有ロック内で公開世代全体を読み取り専用で照合します。保留中、最低版を
下回る現在版、混合ファイルを拒否し、許可台帳は空のままです。実入口への
結線と電源断後の実ストレージでの復旧は今後の検証項目です。

専用 Linux では次のコマンドで、外向き経路のない名前空間で対象試験を
実行できます。

```sh
sudo -n unshare -n -- python3 -m unittest discover -s tests \
  -p test_claude_generation_publication.py -v
CARGO_PROFILE_TEST_DEBUG=0 CARGO_INCREMENTAL=0 \

probe=$(sed -n 's/.*Running unittests src\/lib.rs (\(.*\)).*/\1/p' /tmp/tempest-floor-tests.log)
```

実入口の読み取り専用診断では、管理ディレクトリ内の
`claude-login-publication` が存在するときに公開世代を参照します。
その中の root:root・0600 の `lock` を読み取りで開き、共有ロックを
確保します。保留がなく、`current` が独立した
`claude-login-authority/minimum` 以上の場合に限り、現在版のディレクトリを
固定します。版は正規の正整数表記とし、台帳は世代外に置きます。

世代の `manifest` は設定、署名入力、署名、対象登録、信頼鍵の各ファイル名を
SHA-256 に対応付ける JSON です。信頼鍵は独立した管理側の
`claude-login-authority/trust-key` とも照合し、読み取った同じバイト列を
署名診断に渡します。ディレクトリは root:root・0700、管理ファイルは
root:root・0600・単一リンクとします。公開ディレクトリが存在しない場合
は従来の診断入力を参照します。どちらの経路も起動を拒否します。

独立管理側の `claude-login-authority/approved-generation` には
`revision` と `manifest_sha256` を格納します。共有ロック内で現在版と
承認済み版の一致、および固定世代から読み取った manifest 全体の
SHA-256 の一致を要求します。旧世代の署名済みファイルと manifest 一式を
新版のディレクトリ名に置いても、この照合で拒否します。

### 発行と失効の保証範囲

現行の実入口は、独立した管理鍵による署名、対象・実体・設定の範囲、
期限、管理側が承認した公開世代、台帳に使用済み記録がないことを
診断します。台帳の空きは診断時点の観測です。合成台帳では同じ許可 ID の
消費と失効が排他的な記録を共有し、記録の排他的作成に成功した時点で
競合の順序が決まります。記録と親ディレクトリの同期は成功を返す条件です。
同期に失敗した場合は起動を拒否し、作成済み記録が残っていれば再提示も
拒否します。署名検証だけでは、発行後に起きた失効や承認権限の
変更を確認できません。

運用では管理者が権威ある失効源を定めます。発行側は承認者の権限と失効状態
を最新の管理版で検証し、起動側は最終消費の直前に許可 ID・対象・管理版に
一致する鮮度内の状態を要求します。取得不能、欠落、検証不能、期限到達、
版・対象の不一致、失効済みの場合は台帳の消費や起動に進みません。失効と
消費の順序は同じ権威ある状態で確定する必要があります。Rust の合成試験は
検証済み状態の有無と既存台帳との組み合わせを確認します。失効源の取り込み
と運用上の同期は未実装です。

公開世代の読み取り専用診断では、独立管理ディレクトリの
`revocation-state`、`revocation-signature`、`revocation-key` を固定 FD
から読みます。失効状態には承認済み版、manifest SHA-256、許可 ID、
対象 ID、発行時刻、有効期限、失効有無を含めます。署名の用途を引渡しと
分離し、失効診断用の鍵で検証します。試験用の窓は発行時刻より後の期限で
最大30秒です。未来の発行時刻や期限到達を拒否し、固定実体と台帳の
診断を終えるまでに許可・失効状態の早い方の期限に達した場合も拒否します。

同じ承認済み版・manifest・許可・対象に一致する署名済みの非失効状態は、
より新しい状態が発行された後でも、その有効期限内なら再提示できます。
この診断は、運用上の最新失効状態を保証する仕組みをまだ持ちません。
運用での単調な失効版や消費と同じ権威ある状態での確定は別途検証します。
診断は台帳に書き込まず、起動を拒否します。

固定時刻の回帰試験では、発行時刻と期限が同値の場合、期限に到達した
場合、正しい署名でも manifest・許可 ID・対象が異なる場合の拒否を
確認します。

```sh
cargo test --offline --locked -p tempest-linux-probe \
  signed_revocation_state_checks_scope_and_fixed_time_boundaries
```

専用 Linux の外向き経路のない名前空間と同一 PTY では、試験鍵を使い、
欠落、別用途の署名、同値期限、版違い、失効済み、正常の6件を確認しました。
全件で実入口は終了コード1、台帳は空でした。strace で書き込み・子生成・
ソケット作成がないことも確認しました。

### 失効状態の確定記録（合成検証）

失効状態の更新では、管理側の独立領域に単調な最低失効版と、確定失効版・
状態全体のダイジェストを保持します。排他ロック内で保留を同期し、最低失効版を
引き上げて状態を同期します。保留削除と公開側の親同期を完了した後に、独立した
確定記録を更新します。読者は共有ロック内で、下限と確定版・ダイジェストの
両方を照合します。保留が見えなくても、一致しなければ拒否します。

合成試験では保留削除後の親同期エラーを注入し、排他ロックを保持した更新
プロセスを終了させます。読者は再オープン直後から拒否し、台帳は変化しません。
管理側が対象の状態を確認・同期して確定記録を更新した後だけ読み取れます。
これは試験用ファイルと注入エラーによる検証で、運用の署名診断への結線、
独立領域自体の電源断耐性、実ストレージでの復旧は未検証です。

独立側の確定レコードも、置換直後に新版が見えるだけでは親同期の成功を
示しません。合成モデルでは共有ロック内で、状態と確定記録の照合に加えて
独立側の親を同期し、その呼び出しが失敗した場合は読者側も拒否します。
この条件は、更新側が確定レコードを置換する前にファイル内容と公開側を
同期し、独立側の親同期が耐久性を保証するストレージを前提とします。
同期不能な読み取り専用環境では、別の権威ある確定証明を得られるまで
拒否します。注入エラー後に同期が成功した試験は、実ストレージ障害後の
同期の回復や電源断耐性を証明するものではありません。

Rust 診断では独立管理ディレクトリの `revocation-minimum`、
`revocation-committed` と `revocation-pending` を参照します。
署名済み状態の `revocation_revision` は公開世代の番号とは独立です。
保留が存在する場合、最低失効版未満の場合、確定版または
`state_sha256` が一致しない場合は拒否します。ダイジェストは用途
プレフィックスを含む署名対象全体について計算します。照合後も共有ロックを
保持し、同じ管理ディレクトリ FD を読み取りで開き直して同期します。
同期不能なら拒否し、台帳には書き込みません。

台帳順序の Rust 合成試験では、実際の台帳関数を共通の排他ロック内から
呼びます。失効先行では後続消費を拒否します。消費先行で既存記録に当たった
場合は、失効処理自身が作った保留を解除・同期します。この衝突は稼働中の
子の終了証明にならず、試験では子が引き続き稼働することを確認します。
台帳ディレクトリ同期を記録作成後に失敗させるケースでは保留と記録を残し、
別プロセスで保留中の再提示と台帳の排他的作成をそれぞれ拒否します。

合成 CONNECT の TLS 検証は、ローカル試験サーバーと試験証明書を使い、
既存の CONNECT 判定とバイト中継を通します。クライアントが受け取った
証明書を試験サーバーの証明書と照合し、同じ接続先で検証名だけを変えた場合は
TLS クライアントが拒否すること、別の CONNECT 宛先は上流への接続前に
拒否されることを確認します。試験には OpenSSL、Python 3、timeout が
必要です。ループバックだけを有効にした名前空間で、Rust テストバイナリの
`fixed_connect_relays_tls_certificate_for_client_validation --ignored` を実行します。

署名付き PTY と TLS を同一世代で確認する場合は、外向き経路のない
mount/net 名前空間でループバックを有効にし、専用の作業・設定親を
空の tmpfs にしたうえで、次のスモークを実行します。Python の TLS
プローブは固定合成子と同じ netns と UID で動作します。固定子の
CONNECT と直接接続拒否、プローブの証明書一致と名前不一致拒否、
同じ許可 ID・世代の切断後の回収を照合します。OpenSSL、nsenter、
setpriv を使用し、上流はローカルの試験サーバーです。

```sh
cargo build --offline --locked -p tempest-linux-probe
sudo -n python3 integration/claude_local_auth_pty_smoke.py \
  target/debug/tempest-claude-offline-local-auth-pty --signed-tls
```

同じスモークの期限切れケースでは、許可 IP 版を束縛した署名付き
ダミー許可の単調期限をゲートウェイに渡します。TLS 認証と固定応答を
確認したトンネルを開いたまま期限を待ち、両端の終了と、同じ世代での
次の CONNECT が上流接続なしで拒否されることを確認します。その後に
PTY を切断し、同じ許可 ID と作業・設定世代の回収を照合します。
運用上の失効配布や DNS の変更通知は別の検証対象です。

公開 CLI の拒否だけを確認するには、Linux で `strace` と `ip` を用意し、
次の試験を実行します。試験は外向き経路のない専用 mount/net 名前空間で
ダミー設定と空の台帳を使用します。

```sh
cargo build --offline --locked -p tempest-linux-probe
sudo -n python3 integration/claude_manual_login_refusal.py \
  target/debug/tempest-claude-manual-login
```

余分な引数、入力のリダイレクト、出力・標準エラーが別 PTY の場合、PTY
マスターを拒否します。同一 PTY と有効な設定に対しても、HOME・設定先・
プロキシ・PATH を変更した場合を含め起動を拒否します。全ケースで、子の
生成・通信・設定や台帳の変更がないことを確認します。

4. 終了証拠の欠落、対象不一致、未知のファイルやリンクがあれば、

   隔離を続ける。認証が成立した可能性がある場合の取消は owner が判断する。

### 運用開始前の判断と記録

管理者演習に対応する運用手順案です。現行の公開 CLI は読み取り専用の
最終診断が通っても起動を拒否します。手順案の採用、実設定の変更、
実ログインの実施は個別に判断します。

管理者は開始前に、通信の原本と変更承認者、世代の配布担当、許可の発行・
失効担当、台帳と監督の担当、停止・廃棄・隔離解除の連絡先と代行者を
決めます。担当者の指名、許可期間の上限、記録先のアクセスと保持期間、
失効と消費を直列化する権威と復旧手順も管理者の判断事項です。
owner は管理者と実施範囲、公式ブラウザーからの引き継ぎ、初回非保持と
廃棄条件を確認し、手動ログインを個別に承認します。認証成立の可能性が
ある場合の取消は owner が判断します。

通信の変更は原本との差分を承認してから新しい版を発行します。管理 DNS
応答と承認版の許可 IP の共通部分だけを使用し、接続先の peer を再照合
します。候補なし、版不一致、公開保留、期限切れでは開始を拒否し、
稼働中の許可変更では通信を停止して世代を再確認します。

失効源の管理記録は許可の状態を確定し、ローカル消費台帳は同じ ID の
再提示を排他的に閉じます。順序を確定するには、同一の権威ある状態の下で
対象・許可 ID・管理版・失効版を照合し、失効と消費を共通の排他境界で
直列化します。消費成功には記録と親ディレクトリの同期が必要です。
失効先行なら開始を拒否します。消費先行後の失効では対象実行を停止し、
終了の証拠を別に取得します。状態の取得・照合・同期が失敗した場合や
順序が不明な場合は開始を拒否し、作成済み記録を保持して再提示を拒否します。
現行の合成試験はこの順序を検証します。実運用の権威と復旧手順は未確定です。

異常・失効・期限・PTY 切断では、対象ゲートウェイを停止して新規利用を
拒否します。初回は認証情報を保持せず、同一世代と終了証拠を確認した
対象だけを廃棄し、他世代と消費済み記録の維持を確認します。終了不明や
証拠不足では隔離と再利用拒否を継続します。専用 Linux 管理者が同一世代の
独立した証拠を再確認して解除・廃棄を判断し、時刻・根拠を実施票に残します。

固有の DNS や IP はこの文書に記載せず、運用時は承認済み原本を参照します。
cc-sakura に共有するのは判断の要約と参照先です。認証ファイルの内容・
ハッシュ、認証 URL・コード、端末出力は採取しません。

### VM 外の消費確定と復旧

専用 Linux 管理者が VM の寿命から独立した永続台帳を管理します。
許可 ID は台帳内で一意とし、発行時に対象登録 ID、実行世代、管理版、
失効版、期限に結び付けます。消費と失効は同じ書き込みトランザクションで
発行済みの行から条件付きで遷移させます。VM 内の記録は照合に使います。
開始可否を決める権威は VM 外の台帳です。

1. 開始前に台帳の同一性と有効な発行行を確認します。台帳が読めない、
   初期化されていない、整合しない、または版・期限が異なる場合は拒否します。
2. ホストが消費と照合保留を同じトランザクションで永続化します。
   確定を確認した後、同じ対象登録 ID・許可 ID・実行世代を VM 内で
   永続化し、受領記録をホストへ返します。照合成功とその確定を確認して
   から、将来の監督側が起動可否を判断します。確定応答の喪失や照合の
   失敗では起動を拒否し、許可 ID を再発行しません。
3. 再起動・VM 喪失後は VM 外の消費済み状態を維持します。ゲスト記録の
   欠落や不一致、同一世代の終了証拠の不足があれば隔離を継続します。
   終了証拠は実施票およびホスト側の監査記録と照合し、専用 Linux
   管理者が解除を判断します。解除後も消費済み ID の再利用を拒否します。

将来の実装では、欠落時に空の台帳を自動作成せず、復元した台帳が
確定済み消費を巻き戻さないことを確認できる復旧手順が必要です。
実施票の保持期間は作成から90日とし、未解決の調査に関係する記録は
解決まで保全します。再利用を防ぐ台帳上の状態には実施票の削除を
連動させません。公開 CLI は従来どおり起動を拒否します。

既存の `integration/claude_manual_login_refusal.py` は公開 CLI の拒否、
ローカルの消費済み ID と失効済み ID の拒否、診断による台帳の非更新を
検査します。`synthetic_recovery_record_requires_matching_termination_evidence`
は合成終了証拠の突合を検査します。追加する試験では独立したホストと
ゲストの記録を用意し、消費確定直後のゲスト喪失、台帳の欠落・破損、
照合前後の中断、同一世代の終了証拠の欠落を注入します。再起動後の
同一 ID の拒否と、終了証拠が揃うまで隔離が継続することを別々に確認します。

#### QEMU での固定ダミー試験

Linux x86-64 ホストに Python 3.11 以上、`qemu-system-x86_64`、
`cpio`、静的リンクの x86-64 BusyBox、読み取り可能なローカル Linux
カーネルを用意します。カーネルは gzip initramfs とシリアルコンソールに
対応しているものを使います。リポジトリのルートで次を実行します。

```sh
python3 integration/qemu_host_permit_ledger.py \
  --kernel /path/to/readable/vmlinuz --busybox /usr/bin/busybox
```

TCG で新しい VM を2台順に起動します。ゲストへの配送にはシリアルだけを
使い、NIC・ディスク・共有ディレクトリは接続しません。ホストはテスト専用の
一時 SQLite 台帳で固定 ID の消費を確定してから、最初の VM に試験用の
終了指示を送ります。消費確定の応答は送信しません。最初の VM の終了と、
別 VM からの再提示拒否をそれぞれ確認し、最後にホスト台帳を再読込します。
試験終了時に一時台帳と initramfs を削除します。この試験の対象は VM
を作り直したときの拒否で、ホスト再起動後の台帳復旧は別の検証項目です。

#### ホスト側の確定記録照合試験

`python3 integration/host_permit_receipt_offline.py -v` を実行します。
Python 3.11 以上と `image/requirements.txt` に含まれる cryptography が
必要です。固定試験鍵で署名した消費確定記録を、ホストが発行する単回の
要求値、対象登録 ID・許可 ID・管理世代、および別入力の確定番号と
ダイジェストに照合します。この試験では確定記録をメモリに用意します。
実運用の永続化・配送および公開 CLI への接続は別の検証項目です。

上記の QEMU 試験に `--verify-receipt` を付けると、SQLite 台帳の
消費確定後に別のホスト管理ディレクトリへ確定番号とダイジェストを保存し、
新規ホストプロセスで読み直します。正常対照の後、別要求への応答の再提示、
照合点の欠落・破損、消費前の台帳の復元を拒否することを確認します。
このオプションには cryptography が必要です。管理ディレクトリは試験用で、
台帳と管理記録を同時に巻き戻せる環境への耐性は検証範囲外です。

#### 専用 Linux ホストの管理入力診断

`tempest-host-login-diagnostic` はホスト管理者向けの読み取り専用の
受け口です。専用 Linux ホスト上の信頼された管理環境でのみ使用します。
固定の `/var/lib/izanagi-tempest` 配下から、管理側の検証鍵
（`host-login-authority/verification-key`）と独立確定点
（`host-login-recovery/checkpoint.json`）を読み取ります。入力を指定する
引数・環境変数・ゲストから引き継いだ FD は使用しません。管理ディレクトリは
root 所有でモード 0700、入力は root 所有の通常ファイルでモード 0600 です。
確定点は正の `sequence` と小文字16進64桁の `digest` を持ちます。

管理側は `host-login-authority/scope.json` に対象登録 ID、許可 ID、
管理世代を置きます。診断は毎回32バイトの要求値を生成し、標準出力に
小文字16進で1行出力します。ホストの管理プロセスは標準入力に
`challenge`、`commit`、16進の Ed25519 `signature` を含む JSON を
1行（改行込み4096バイト以内）で返します。署名の対象は固定ダミー試験
`integration/host_permit_receipt.py` の形式です。単独診断の応答読み取りは5秒を上限とします。診断は固定入力と照合し、
正常でも終了コード1を返します。実運用の応答経路は未配備です。
公開ゲスト CLI とは独立しており、試験では隔離したマウント名前空間内の
管理領域を使い、別プロセスが固定試験鍵で応答します。

```sh
cargo build --locked -p tempest-linux-probe --bin tempest-host-login-diagnostic
sudo python3 integration/host_login_diagnostic_readonly.py \
  target/debug/tempest-host-login-diagnostic
```

試験には Linux の `unshare`、`mount`、`strace` と Python の cryptography が必要です。

`tempest-host-login-responder` は専用 Linux ホストで、診断の要求値を
標準入力から1行読み取ります。固定管理領域の
`host-login-ledger/record.json` と SQLite 台帳の最新行を、独立した
確定点と管理スコープに読み取り専用で照合します。対象が消費済みで、
番号とダイジェストが一致する場合に限り、`host-login-signer/signing-seed`
の32バイトの Ed25519 シードを使って応答を署名します。シードから導出した
公開鍵が管理側の検証鍵と異なる場合も拒否します。起動や台帳更新は行いません。

```sh
cargo build --locked -p tempest-linux-probe \
  --bin tempest-host-login-diagnostic --bin tempest-host-login-responder
sudo python3 integration/host_login_diagnostic_readonly.py \
  target/debug/tempest-host-login-diagnostic target/debug/tempest-host-login-responder
```

統合試験は読み取り専用の試験領域で2つのバイナリを接続し、未確定、
台帳の巻き戻し、応答喪失での拒否を確認します。実運用への配備は別の作業です。

`tempest-host-login-publisher` は固定管理領域の
`host-login-ledger-source/ledger.sqlite3` を読み取り専用の単一
トランザクションで照合し、確認済みの行から `host-login-ledger/record.json`
を生成します。排他ロックは SQLite の読み取り開始から公開の同期完了まで
保持します。台帳・確定点・スコープの更新側も公開先の root 所有、モード
0600 の固定 `lock` を共有します。応答側は共有ロックの下で SQLite の
最新行を読み直し、公開済みレコードと照合してから署名します。公開後に
許可が失効した場合は、古い確定点と公開レコードが残っていても拒否します。

公開時は `pending` を永続化し、同期済みの `record.new` をアトミックに
置き換えます。ディレクトリの同期を確認してから `pending` を除去します。
中断で `pending` が残る場合は署名を拒否します。復旧は管理者がロックを
取得し、元台帳と独立確定点を確認したうえで判断します。

```sh
cargo build --locked -p tempest-linux-probe --bin tempest-host-login-diagnostic \
  --bin tempest-host-login-responder --bin tempest-host-login-publisher
sudo python3 integration/host_login_diagnostic_readonly.py \
  target/debug/tempest-host-login-diagnostic target/debug/tempest-host-login-responder \
  target/debug/tempest-host-login-publisher
```

#### ホスト台帳から確定済みスナップショットを読む

`tools/host_ledger/schema.sql` は SQLite 3.37 以降のホスト管理用台帳の
形式です。確定番号は台帳内で一意とし、各行に台帳 ID、対象登録 ID、
許可 ID、管理世代と状態を保持します。台帳管理側は共通の排他ロックで
更新を直列化し、ロールバックジャーナル方式を使います。

`tools/host_ledger/read_snapshot.py` は固定管理領域の
`host-login-ledger-source/ledger.sqlite3` を共有ロックの下で読み取り専用で
開きます。一つの読み取りトランザクションで許可の最新行を取得し、
消費済み状態、管理スコープ、独立確定点との完全一致を確認した場合だけ、
照合済みの JSON を標準出力に返します。台帳が欠落している場合は拒否し、
自動作成しません。通常の公開・署名経路は上記の Rust バイナリです。

```sh
python3 integration/host_ledger_snapshot_offline.py -v
```

#### 固定スコープの発行・消費・失効

`tools/host_ledger/write_transition.py` は専用 Linux ホスト管理者向けの
固定操作です。固定の `scope.json` と `host-login-authority/ledger-id.json`
（台帳 ID の JSON 文字列）を使います。引数は `issue`、`consume`、
`revoke` のいずれかです。初回は管理側がスキーマで作成した空の台帳と、
同じ台帳 ID・スコープに対する確定番号0、状態 `empty` のダイジェストを
持つ独立確定点が必要です。

台帳の最新行が独立確定点に一致するときだけ、共通排他ロック内で SQLite の
新しい行を同期・確定し、独立確定点を原子的に置き換えて同期します。
失効後の消費、二重消費、同じ許可 ID の再発行を拒否します。途中で中断して
台帳と確定点に差が残った場合は、自動修復せず、次の遷移・公開・署名を
拒否します。ホスト管理側が独立した証拠を照合して復旧を判断します。

隔離統合試験では、既存の3つのバイナリに書き込みスクリプトを追加で渡します。

```sh
sudo python3 integration/host_login_diagnostic_readonly.py \
  target/debug/tempest-host-login-diagnostic target/debug/tempest-host-login-responder \
  target/debug/tempest-host-login-publisher tools/host_ledger/write_transition.py
```

#### 同一ホストでの PTY と管理応答の照合

`tempest-combined-login-diagnostic` は専用 Linux ホスト上の管理者の
同一 PTY で、既存の署名付き公開世代を読み取り検証します。その後、同じ
PTY で単回要求値を出し、ホスト管理側の署名応答を1行読み取ります。
要求値の出力と応答の読取には許可と失効記録のうち早い方の絶対期限を
使います。無応答、途中入力、PTY の出力キュー満杯でも期限で拒否し、
公開世代の共有ロックを解放します。結果の表示はロック解放後に行います。
署名済みの対象登録 ID・許可 ID・管理世代を公開世代の検証結果と照合し、
ホスト台帳と既存の失効記録を読み直します。正常な場合も既存の起動拒否で
終了コード1を返します。この診断は参加 VM 側の公開 CLI と独立しています。

次の統合試験は、固定 CLI 実体を読み取り専用かつ実行不可でマウントし、
隔離した名前空間内で管理側の署名応答を PTY に配送します。固定実体は
既存の署名付き公開試験と同じものが必要です。

```sh
cargo build --locked -p tempest-linux-probe --bin tempest-combined-login-diagnostic \
  --bin tempest-host-login-responder --bin tempest-host-login-publisher
sudo python3 integration/combined_login_diagnostic.py \
  target/debug/tempest-combined-login-diagnostic target/debug/tempest-host-login-responder \
  target/debug/tempest-host-login-publisher
```

統合診断から固定ダミーの回収まで試験する場合は、上の統合試験に
`target/debug/tempest-claude-offline-local-auth-pty` を第4引数として追加します。
試験ハーネスは固定ダミーの署名済みハンドオフと同じ許可 ID・対象で管理
世代1の公開記録を用意し、不一致では固定ダミーを起動しません。一致した
場合だけ既存の固定ダミー試験を実行し、同じ許可のローカル消費記録と、
実際の作業・設定ディレクトリの識別情報を回収証拠に照合します。終了証拠を
落とす対照では、停止後も同じ実行世代を隔離します。外向きルートのない
試験専用名前空間と一時作業領域を使用します。

この第4引数の試験では、照合が通った別の固定ダミー許可を使う
`signed-tls-staged` 対照も実行します。同じ監督が固定 CLI と依存を
検証済み FD から配置し、新規設定世代と専用 PTY で BusyBox を起動し、
ループバック上の試験 TLS を透過中継します。BusyBox の固定スクリプトは、
同じ専用 root に配置した検証済み OpenSSL と依存2点を使い、子の実行境界内
から TLS を開始します。認証には試験用 CA だけを用意し、CA が欠落した場合は
配置・消費の前に拒否します。別の CONNECT 宛先、直接接続、TLS 名不一致を
拒否し、切断後に同じ許可 ID と両世代の回収証拠を照合します。
固定 CLI は実行不可でマウントします。統合診断から固定ダミーケースを
開始する境界は、この試験ハーネス内にあります。

固定実体を配置する既存のダミー PTY 対照では、監督側が起動前に固定 CLI、
ローダー、glibc 5点の FD を検証して保持します。専用 root を作った側は
元の固定パスを開き直さず、FD の内容を再ハッシュしながらコピーして
読み取り専用でマウントします。この経路で実行するのは固定ダミーだけです。
同一ホスト診断の公開入口は従来どおり起動前に拒否します。

`pinned_login_artifact_set_stages_without_executing` は専用 Linux の固定
成果物と root 所有の一時作業・設定領域を使う除外テストです。不足した
FD セットで配置が始まらないこと、全点を配置した場合も実行なしで
新規設定世代をマウントし、解除後に同じ世代を回収できることを確認します。

`integration/combined_login_diagnostic.py --staging-test` は、通常の診断
バイナリの位置に `tempest-linux-probe` のライブラリテスト実行ファイルを
指定して実行します。テストは実際の統合診断が保持する固定 CLI の FD に
検証済み依存 FD と管理世代を結び付け、その FD セットを隔離した配置へ
渡します。元パスを差し替えても元の FD から配置できること、同じ inode
の内容変更・依存不足・管理世代違いを拒否することを確認します。内容変更に
使うのは tmpfs 内の試験コピーです。固定実体は起動せず、配置の後に
マウントを解除して新規設定世代を回収します。
